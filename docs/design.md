# 1. 问题定义与目标

本文设计一个 DSH 插件，用来解决「长对话中用户已明确提出的要求被遗忘、被选择性遵守、或在新旧口径之间执行了旧的那一个」的问题。作用域限定在**单个会话的单个对话内**，不考虑跨会话记忆。

## 1.1 现象与失效链条

用户视角的抱怨通常是这三种说法，它们背后是三条不同的技术链路：

| 用户说法 | 实际链路 | 现有机制的缺口 |
| --- | --- | --- |
| 「我早就说过要用中文」 | 规则消息在很久之前，被后续几十轮工具输出挤出注意力 | 上下文里没有任何常驻结构，只有原始消息 |
| 「我已经改成方案 B 了」 | 旧的「用方案 A」与新的「改 B」同时在上下文里，没有取代关系 | 日志是追加式的，模型只能靠读得更仔细来分辨先后 |
| 「你嘴上答应了，做出来的又是另一回事」 | 模型产出符合规则的自然语言，但工具调用违背规则 | 没有任何对工具调用的规则校验 |

三条链路必须分别解决。只做第一条（把规则贴得更近），第二条和第三条依然会发生；这是本次设计中「分层」的直接原因。

## 1.2 现有机制为何不解决

- **system prompt 口诀**：写「请记住用户的所有要求」属于让被考核者自己划重点，已被实践证伪。
- **会话压缩（compaction）**：压缩的目标是省 token，不是保真；它会让早期规则以摘要形式存在，而摘要无法表达「哪一条现在是生效的」。
- **goal**：goal 是单目标状态机（active / paused / blocked / complete），语义是「这件事做到什么程度算完成」，不是「一组长期有效的约束」。把规则塞进 goal 会让 `complete` 变成一种奇怪的规则失效方式。
- **让模型自己维护记忆文件**：与本问题同构——失效点正是「选择性记忆」，把这项判断交回模型不会改善。

## 1.3 设计目标

1. **每一步都在**：生效中的规则必须出现在每一次模型请求里，不依赖模型的检索意愿。
2. **可推翻**：后出现的要求要能明确取代先前的同类要求，且「谁取代了谁」在界面上可查。
3. **可回溯**：台账里的每一条都能定位到产生它的会话事件序号与原文，模型的理解只是原文的一个视图。
4. **可恢复**：进程重启、会话恢复、历史压缩之后，台账必须逐字节一致地重新算出来。
5. **可扩展但默认克制**：默认只做「提示」，只在规则可以被机器判定时才升级为「拦截」。

## 1.4 非目标

- 不做跨会话、跨工作区的长期记忆。
- 不做历史改写。旧结论不从日志里删除，只标记为已被取代，审计线索保留。
- 不替代 agent preset、skills 或 goal；它是与它们正交的一层。
- 不在 P0 阶段引入任何额外的模型调用。

## 1.5 什么算「用户的明确要求」

这是整个设计里最容易翻车的一步：判宽了，把闲聊固化成枷锁；判窄了，漏掉真正的要求。本设计采用**三类准入**，而非「全部让模型判断」：

1. **显式声明**（最高置信）：`/rule` 命令、`记住：…`、`以后都…`、`必须…`、`不要…`、`一律…`。
2. **字面可锚定**：包含路径、命令、包名、URL、端口、语言名等可以精确匹配的字面量，且语气为祈使。
3. **模型归类**（最低置信）：对前两类产出的候选做补全与去重，不负责从零发现规则。

不同类型的指令在台账中分型存储，这一点决定了它们会不会变成永久枷锁：

- `rule`：长期有效（「回答用中文」「不要修改 `D:\prod`」）。
- `preference`：风格偏好，可被后续同类偏好取代。
- `decision`：本任务内的结论（「用方案 B」），随新结论自动取代，且不会跨任务残留。
- `ban` / `pin`：禁止项与用户手动固定项，`pin` 的权重最高。

一个 `decision` 一旦被当作 `rule` 存储，就会在下一轮需求变更时表现为「模型抱着老方案不放」——这正是用户抱怨的第二种现象。因此分型不是洁癖，而是正确性要求。

# 2. 方案设计

## 2.1 分层总览

```
user/message ──┬──> [L1 派生] sessionProjections: directiveLedger（纯函数 fold）
command/run ───┘         │
                         ├──> [L2 抽取] 确定性候选 + 可选模型归类（带缓存）
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
 [L3 注入] 常驻可见                 [L4 执法] 可判定项的硬边界
 systemPrompt.context()             ctx.tools.guard()
 agent/pre-step 开场短提醒           turn 收尾自检
        └────────────────┬────────────────┘
                         ▼
                 [L5 可见性] 面板 / Turn 摘要 / `/rule` 命令
```

数据只朝一个方向流动：日志 → 派生 → 展示与执法。除 L2 的归类缓存之外，没有任何可写状态参与「模型看到什么」的决策。

## 2.2 数据模型

台账中的一条指令：

```ts
interface Directive {
  id: string                    // 稳定 id，由 sourceSeq + 内容哈希派生
  sourceSeq: number             // 产生它的会话事件序号（原文锚点，不可变）
  turn: number
  quote: string                 // 原文摘录，用于回溯与人工核对
  text: string                  // 规范化后的祈使句
  kind: 'rule' | 'preference' | 'decision' | 'ban' | 'pin'
  scope: 'style' | 'tool' | 'path' | 'workflow' | 'content'
  topicKey: string              // 取代关系的作用域，见 2.5
  authority: 'user-pinned' | 'user-stated' | 'literal-anchored' | 'model-inferred'
  status: 'active' | 'superseded' | 'revoked' | 'retracted'
  supersedes: string[]          // 被本条推翻的旧指令
  supersededBy?: string
  checker?: {                   // 仅在可机器判定时存在
    type: 'path-glob' | 'command-regex' | 'language' | 'forbidden-write'
    spec: unknown
  }
}
```

`status` 有四个值，含义必须区分清楚：`superseded` 是被新指令取代（正常演进），`revoked` 是用户显式撤销（`/rule drop`），`retracted` 是**来源消息本身被历史编辑替换**（例如用 `ask-again` 那条消息改写了原提问）。三者在界面上应该分开呈现，因为用户的预期不同。

## 2.3 派生：台账如何从日志算出

台账是一个 `sessionProjections` 单元，符合宿主对投影的全部约束：`apply(state, event)` 是纯函数、同步、对无关事件返回同一引用，未变化时下游零成本。

关键取舍有三条：

1. **折叠完整事件日志，而不是当前 surface**。压缩会重写 surface（`surfaceOp: replace`），但日志里的事件仍在。若台账从 surface 推导，一次压缩就会让早期规则集体消失——这与设计目标 4 直接冲突。
2. **折叠时尊重 replace 意图**。折叠完整日志不等于无视替换：当某条 `user/message` 被后续事件以 `surfaceOp: { op:'replace', startSeq, endSeq }` 且 `sourceEventSeqs` 覆盖其 `seq` 时，该条指令转为 `retracted`。这既保留了审计，又让「用户改写了那句话」正确生效。
3. **`command/run` 也是输入源**。`/rule` 类命令的输入会随命令生命周期落盘（命令定义需声明 `recordInput: true`），因此 pin / revoke 这类「元操作」同样可以从日志重算，不需要旁路存储，也不需要新增会话事件类型（新增事件类型会破坏会话可重开性，属于禁区）。

派生结果对外通过 `wire.view` 暴露给客户端，客户端只读已算好的结果，不在前端二次折叠事件。

## 2.4 候选抽取

抽取采用**语义判定为主、确定性抽取为辅**的两级结构。这个顺序是实测倒逼的结果，见 2.4.1。

**事实基线：为什么必须让模型判断**

现行版本只有确定性规则时，出现了一类无法靠补规则修掉的误判。用户在讨论定时任务功能时说：

> 固定任务这里应该也有下拉，可以选

`固定` 是产品功能名（定时任务），不是「请把这条钉住」这个动作，但规则表把它认成 `pin`——权重最高、且不会被后续要求取代的一类。同类失败还有：把它整条当成长期要求，而它实际是一次性的 bug 反馈（「这里应该也有下拉」）。

规则可以继续加例外，但每加一条都是对**下一个未知产品名词**的赌注。判断一句话是「一次性任务」还是「长期规则」，依赖的是语义，不是字面。

**第一级：语义判定（模型，必需）**

对每条用户消息做一次结构化判定，产出：

| 字段 | 取值 | 作用 |
| --- | --- | --- |
| `kind` | `rule` / `preference` / `decision` / `ban` / `pin` / `none` | `none` 表示这不是长期要求，最常见且最重要的一类 |
| `text` | 规范化祈使句 | 注入文本 |
| `topicKey` | 内置键表或 `general.<hash>` | 取代关系 |
| `supersedes` | 被推翻的旧条目 | 取代链 |
| `reason` | 一句话理由 | 面板展示，让用户能判断判定是否合理 |

`none` 的判定标准写进提示词，核心是三条：是否指向**当前这一次**任务、是否陈述**功能现状**、是否是**提问**。截图里的两句话三条全中，应当判 `none`。

**第二级：确定性抽取（零成本，作为模型不可用时的降级）**

保留现有规则，但只在前一级失败或关闭时使用，且**把 `pin` 从默认规则里移除**：`pin` 只能来自用户显式操作（`/rule pin`、面板按钮、`固定这条`），不再由任何文本模式推断。

**为什么把成本放在这一级是值得的**

一次小模型的短判定调用，比一次错误的 `pin` 便宜得多。后者的代价是：一条错误的高权重条目进入每一轮上下文，且**不会被后续对话自动取代**（`pin` 的定义就是不被取代），用户只能手动删。以当前部署的上下文窗口衡量，判定调用的成本可以忽略，而误判的影响持续到用户发现为止。

**调用方式与必须遵守的约束**

1. **不进主对话上下文**。判定调用必须是独立的、无历史的消息序列，不能让主对话看见这些中间推理；否则每轮都会污染上下文并膨胀日志。
2. **不经过会被拦截的路径**。本会话中存在拦截未标记 `purpose` 请求的插件，因此判定调用要有自己的可识别的标记，或在独立上下文中发起。
3. **结果必须可缓存**：判定是 `(sourceSeq, contentHash, promptVersion)` 的纯函数。命中缓存时不重复调用；同一段文本永远得到同一判定。
4. **失败不阻断对话**：判定超时或报错时，**降级为确定性抽取**并标记 `authority: 'literal-anchored'`，面板显示「未判定」。绝不因为判定失败就让主对话无法进行。
5. **异步、不阻塞**：判定在消息提交后异步进行，本步不等待它。因此**当轮的台账可能滞后一步**——这是可接受的，因为台账的作用是跨轮次提醒，不是即时生效。

### 2.4.1 为什么最初没有模型判定

原设计（P0）刻意只用确定性规则，理由是「不引入额外模型调用」。这个取舍在实测中被推翻：215 条真实消息里，纯规则方案的误报率约为 8%（17/215），且剩余误报中相当一部分属于「字面正确、语义错误」——补规则只能把它们换成另一种错法。

真正能省的不是那一次调用，而是**误判带来的持续成本**：错误的 `pin` 每轮都在、且不会被自动取代。因此模型判定从「可选优化」升为必需，确定性抽取降级为它的降级路径。

### 2.4.2 判定提示词的质量是唯一真正的风险

引入模型判定后，系统的主要失效模式从「规则漏判」变成「判定本身判错」。这和被判定对象是同一个模型——存在确认偏误的风险：它倾向于认为自己看到的是重要内容。

缓解：

1. **默认倾向 `none`**。提示词明确要求「拿不准时判 `none`」，因为漏掉一条长期要求只是少一条提醒，而误收一条 `pin` 会持续污染。
2. **判定理由必须输出**，并在面板里展示。用户能一眼看出「它为什么觉得这是长期要求」，从而发现系统性偏差。
3. **原文与判定并列**。面板同时显示用户原话和抽取结果，而不是只显示后者。
4. **判定结果可一键纠正**，纠正动作反馈成新的 `pin`/`drop` 命令，进入日志。

## 2.5 话题键与取代链

`topicKey` 是取代关系的唯一依据。它把「同一件事的两种说法」绑在一个槽位上，新值自动把旧值挤成 `superseded`。

内置一组稳定键，避免模型每次生成不同的分类：

| topicKey | 覆盖的例子 |
| --- | --- |
| `output.language` | 用中文回答 / switch to English |
| `tool.package-manager` | 用 pnpm，不要用 npm |
| `tool.test-command` | 测试一律跑 `node --test` |
| `path.forbidden-write` | 不要动 `D:\prod` |
| `workflow.commit-policy` | 提交前先跑 lint |
| `workflow.plan-first` | 改代码前先说方案 |
| `content.format` | 结论写在最前面 |
| `decision.<自定义>` | 任务内的技术选型 |

取代规则：

1. 同 `topicKey` 的新指令 → 旧指令置 `supersededBy`。
2. `pin` 不被自动取代，只能被用户显式撤销或显式重新 pin。
3. `ban` 与 `rule` 不同键，不互相取代。
4. 显式否定式推翻（「刚才那条不算」「改成…」）立即生效，不需要等到下一轮。

## 2.6 注入：让规则每步可见

主通道是 `ctx.systemPrompt.context()`：这是宿主自带的动态运行时上下文入口，内容变化才会落盘一次新的 `user/message` 快照，内容不变则不重复写。这一点决定了**字节稳定性是硬指标**：台账序列化必须按 `id` 排序、字段顺序固定、不含时间戳和随机量；否则每一步都会生成一条新的上下文快照，既污染日志又摧毁前缀缓存命中率。

常驻区格式（示意）：

```
生效中的用户要求（按优先级，共 N 条）：
[R1] 回答一律中文  · 来源 turn 2 · 规则
[R7] 不要修改 D:\prod 下的任何文件  · 来源 turn 14 · 禁止
[D3] 采用方案 B  · 来源 turn 31 · 决定（已取代 D1「方案 A」）
[?] 未归类原文：别再问我要不要继续  · 来源 turn 33
```

辅通道是 `agent/pre-step` 瀑布：仅在 `step === 1`，或本轮用户输入与某条生效规则存在词面重合时，追加一条最多 3 条规则的短提醒消息。改写决策时必须展开原决策（`{ ...decision, messages }`），保留 `startsRequestSeries` 等字段。

预算与降级：常驻区有硬上限（默认 800 token，用 `ctx.tokenMeter` 度量）。超限时按 `pin` → `ban` → 最近使用 → 词面相关度依次降级，被降级的条目在面板中仍然可见并标注「未注入」，不做静默截断。

## 2.7 执法：可判定项的硬边界

只有同时满足「`kind === 'ban'`」和「存在 `checker`」的指令才升级为拦截，使用 `ctx.tools.guard()`：同步、单调、任何瀑布监听都无法推翻，返回字符串即为拒绝理由。

可判定的典型场景：

- 写入路径命中 `path.forbidden-write` 的 glob → 拒绝 `write` / `edit`。
- 命令串命中 `command-regex`（如 `npm install`）→ 拒绝 `pwsh`。
- 安装包名在黑名单 → 拒绝包管理器调用。

拦截理由必须回写 `规则 id + 来源 seq`，让用户一眼看出是自己在哪一轮说过这句话。

非可判定项（语气、格式、语言偏好）一律不拦截。收尾时用 `turn/end` 后的一次轻量对照产出「未遵守提示」：例如声称已改成中文但 `assistant/message` 仍是英文，或声称没动文件但 `workspaceChanges` 里出现了被禁路径。这类提示只记录与展示，不阻断。

## 2.8 交互与可见性

- **`/rule` 命令**（`ctx.commands.register`，不走模型）：`/rule list`、`/rule pin <id>`、`/rule drop <id>`、`/rule add <文本>`、`/rule why <id>`。必须声明 `recordInput: true`，使这些操作自身可被日志重算。
- **侧栏面板**：`sidebar.panellist` 增加入口，`main` 注册页面。列表分组为「生效中」「已取代（折叠显示 旧 → 新）」「已撤销」「已失效（来源被编辑）」，每行显示来源 turn、类型徽章、是否已注入、可跳转。
- **Turn 摘要**：`conversation.chat.turnTail` 挂一行「本轮命中 N 条 / 提示 M 条」，点击展开。
- 面板与摘要都通过 Host 投影的 `wire.view` 取值，客户端不折叠事件。

| Turn 摘要行 | Client `conversation.chat.turnTail` 槽位 | 已核对；放在 P2 |
| 自定义 Chat 行 | `conversation.chat.node` 为固定 key 表，**不复用** | 未采用 |

明确不使用的机制：新增会话事件类型（会破坏会话可重开性）、`system-prompt/assemble` 全量替换（影响面过大）、历史物理改写（破坏审计）。

### 2.9.1 原设计的两处修正

实现过程中，设计文档里的两个选择被实测推翻，记录下来以免后来者重犯：

1. **侧栏面板（`sidebar.panellist` + `main`）改为输入区 dock（`conversation.input.dock`）**。台账是每个会话的状态，放进全局侧栏意味着用户要先跳出对话才能查看；而 `conversation.input.dock` 直接给出 `useProjection`，正好读取 Host 已折叠好的值，且不需要额外的 HTTP 接口。
2. **预算超限的呈现方式**。原设计写「被降级的条目在面板中仍然可见并标注未注入」，但投影的 `wire.view` 是 `state → view` 的纯函数，拿不到预算结果。最终让 `view` 同时读取渲染结果，给每条补 `injected` 布尔值、给整体补 `injected` 计数，面板据此标注——否则面板会声称模型看到了它其实没看到的要求，而这正是本插件要消灭的那类谎言的镜像。

## 2.10 存储、版本与恢复

- **台账本体不落盘**：完全由日志派生，`stateVersion` 用于在字段或折叠语义变化时让旧缓存失效并整体重折。
- **归类缓存**：可选的第二级抽取结果，落在插件自有目录，键为 `(sessionId, sourceSeq, contentHash, promptVersion)`；缓存丢失只影响成本，不影响正确性（未命中即降级为原文直列）。
- **恢复语义**：会话恢复后首次 `stateOf` 会从日志折算出同一份台账；`/rule` 的 pin 与 revoke 也随之重现，因为它们本身是日志事件。
- **兼容性**：台账 JSON 保持纯数据、字段可缺省；未知字段在旧版本读取时被忽略而不是报错。

## 2.11 配置项

```yaml
- id: directive-ledger
  name: '@local/dsh-directive-ledger'
  config:
    budgetTokens: 800          # 常驻区上限
    reminderMode: auto         # off | auto | always
    extraction: semantic       # semantic（默认）| deterministic
    judgeProvider: ''          # 判定的模型路由，空则用默认模型
    judgeTimeoutMs: 8000       # 判定超时；超时降级为 deterministic
    enforce: guard             # off | guard
    dataDir: ''                # 判定缓存目录，空则用默认位置
```

`extraction: deterministic` 只用于诊断或离线环境；它不是「省一次调用」的选项，因为规则方案的误判会持续到用户手动清除。所有可调项都放在 Config 里，用户的 patch 层在升级后保留。

# 3. 评估要点

## 3.1 一个完整演算示例

用户与助手的真实轮次（节选）：

| turn | 用户说 | 台账变化 |
| --- | --- | --- |
| 2 | 以后都用中文回答 | `R1 output.language = 中文`，active |
| 9 | 用 npm 装依赖吧 | `R2 tool.package-manager = npm`，active |
| 14 | 不要动 `D:\prod` 任何文件 | `B1 path.forbidden-write = D:\prod`，ban + checker |
| 21 | 算了，还是用 pnpm，别再提 npm | `R2` → superseded；`R3 = pnpm`，active，`supersedes: [R2]` |
| 31 | 方案改用 B | `D1 方案 A` → superseded；`D2 方案 B`，active |
| 38 | （工具调用尝试写 `D:\prod\x.json`） | guard 拒绝，理由含 `B1 · turn 14` |

到 turn 38 时，常驻区只有 `R1 / B1 / R3 / D2` 四条加一条「已取代 D1」。这正是「不遗忘、不执行旧结论、且能拦住实际动作」的最小验证形态——**建议把它作为验收夹具的第一条**。

## 3.2 三项决策的最终结论

### 3.2.1 是否引入额外的模型调用做语义判定

- **结论：引入，且是必需路径。** 不是「可选优化」，而是抽取决策的主路径；确定性规则降级为它不可用时的兜底。理由与实测依据见 2.4.1。
- 代价：每条用户消息一次短判定调用（结果可缓存，同一段文本只算一次）。
- 收益：能判出「这不是长期要求」，而这正是纯规则方案无法可靠回答的问题——它只能匹配字面，无法识别「固定任务」是产品功能名。
- 由此引入的新风险与缓解措施见 2.4.2：默认倾向 `none`、必须输出理由、原文与判定并列、可一键纠正。

### 3.2.2 违规是拦截还是先做后报

- 倾向：只有 `ban` + 可判定 `checker` 才拦截，其余一律提示。
- 理由：拦错一次（把合法操作判成违规）比忘一次伤害更大，且用户会立刻失去对插件的信任。
- 若要求全拦截：需要为每一类规则手写判定器，成本与误报率都会上升。

### 3.2.3 `decision` 类结论的作用域

- 倾向：直到被新结论推翻为止，但仅在本会话内；会话结束即失效，不写回配置或 memory。
- 另一选项：本轮任务结束即失效。风险是模型在下一轮又回到默认行为，用户会认为「又忘了」。
- 这个选择直接决定用户感知，建议按「会话内长期」实现，并在面板里提供一键清除。

## 3.3 已否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 自动摘要用户消息后回填 | 丢取代语义；概括即失真；无法回答「现在生效的是哪条」 |
| 把规则写进 goal | goal 是单目标状态机，`complete`/`blocked` 与规则生命周期语义冲突 |
| 依赖模型自查并复述规则 | 与本问题同构，失效点正在这里 |
| 每条规则在每步都注入全文 | token 线性膨胀，且摧毁前缀缓存命中；必须做预算与降级 |
| 改写历史、删除旧结论 | 破坏审计；用户需要看到「我改过」，只是不希望模型执行旧的 |
| 新增会话事件类型承载台账 | 会话重开会被拒；宿主明确保留该能力给实验包 |

## 3.4 风险与失效模式

- **误判为规则**：普通的假设句被固化。缓解：三类准入分级 + 面板一键撤销 + `model-inferred` 条目默认低权重。
- **取代链断链**：`topicKey` 生成不稳定，导致旧规则没被挤掉。缓解：内置键表 + 面板手动合并 + 断言「同键只能有一条 active」。
- **常驻区抖动**：序列化不稳定导致每步都写新快照。缓解：确定性序列化 + 单测断言「内容不变 → 上下文文本逐字节相同」。
- **预算挤压**：规则过多时关键条目被降级。缓解：`pin` 优先 + 面板显示「未注入」 + 超限告警。
- **guard 误拦截**：glob 写错导致合法写入被拒。缓解：P0 只支持绝对路径前缀与显式通配，面板提供「试算」按钮。
- **与历史编辑插件的交互**：`ask-again` 改写原提问后，旧规则应失效而非继续生效。缓解：折叠时处理 `sourceEventSeqs`，产生 `retracted` 状态。

## 3.5 分期与验收

| 阶段 | 内容 | 验收标准 | 状态 |
| --- | --- | --- | --- |
| P0 | 确定性候选抽取 + 台账投影 + 常驻注入 + `/rule` 命令 | 重启后台账逐字节一致；任一步的请求里都能看到全部 active 规则；上下文文本在无变更时不重写 | 已上线并通过真实会话回放 |
| P1 | 取代链 + 面板 | 3.1 的夹具里 `R2 → R3`、`D1 → D2` 正确显示，且只有新值 active | 已上线（面板为输入区 dock，见 2.9.1） |
| P2 | guard 拦截 + 收尾自检 | 被禁路径写入被拒且理由含规则来源轮次；未遵守项在 Turn 摘要中出现 | 拦截已上线；收尾自检待做 |

P0 不含任何额外的模型调用，也不含任何新的会话事件类型，因此可以在现有运行时上直接安装与回滚。

### 3.5.1 实现期得到的实测结论

以下几项原设计没有预见，是拿真实会话日志（13300+ 事件、215 条用户消息）回放后才发现的：

- **标记词必须出现在句首**。原设计只说「祈使与绝对语气模式」，实测把 `看你几乎每次回答问题都清理残留…`、`这个问题一定要解决掉`、`怎么从机制上让每次端到端运行完…` 全部误判成长期要求。现在的判据是：句首窗口（12 字符）内出现标记，或整句短于 30 字符且不以叙述/疑问开头。
- **逗号不是子句边界**。`一级标题只用于划分顶层主题，不得写成要点` 是一句完整约束，按逗号切开会让主语丢失；但 `对象是：每一轮的对话，不用考虑跨对话` 又确实需要去掉冒号前缀。现在的做法是按终止符切分，再判断逗号前是否是「标签」（短且非祈使）。
- **禁区与要求必须分槽**。`算了，还是用 pnpm，别再提 npm` 同时表达「改用 pnpm」和「禁止 npm」。原设计让它们共享 `tool.package-manager`，结果禁令会把刚下达的指令一并取代。现在禁令统一加 `ban.` 前缀独立成槽。
- **路径禁令的槽位要含路径**。否则「不要动 A 目录」会被后来的「不要动 B 目录」取代，A 的保护静默消失。
- **抽取规则变更等于折叠语义变更**，必须同步 bump `stateVersion`，否则持久化投影缓存会继续提供按旧规则产出的结果。
- **面板必须复用宿主的布局变量，不能写死像素**。首版卡片没有宽度约束，在通栏的 `conversation.input.dock` 里铺满整个对话列，与居中的输入框明显错位。修法是照抄宿主自己的算法：输入框外层容器有 `padding: 0 var(--dsh-composer-side-clearance)`，卡片自身 `max-width: var(--dsh-composer-card-max-width)` 且 `margin: 0 auto`。卡片以 `width: calc(100% - 2 * clearance)` + 同样的 `max-width` + `margin: 0 auto` 复现这段几何，用户拖动列宽或窗口时自动跟随。
- **同一槽位里的邻居是最可靠的样式参照**。`conversation.input.dock` 里的 `TodoPanel` 也是一张卡片，它的 CSS 规则直接给出了这个槽位的正确几何，比推测「该多大」可靠得多。

### 3.5.2 与宿主其他插件共存的运维教训

这一条与本插件的代码无关，但它是排查过程中真实发生的，记录下来避免重犯：

- **崩溃表象会指向无关的邻居**。某次重启报 `web boot: 1 entry did not activate / dsh-remote: import failed`。核查结论：`dsh-remote` 默认 `updateMode: 'auto'`，会定时从 npm 拉新版本 tarball、逐个 rename 覆盖自己的 `lib/*.js`，然后热替换运行中的 Host 半。崩溃发生在写入窗口内。磁盘上的文件与官方 tarball 逐字节一致（35 个文件 SHA256 全部相同），不是安装损坏。
- **`node_modules` 里的运行时标记会被 pnpm 清掉**。用 `update-mode` 文件关闭自更新，对下一次 `pnpm install` 无效——该目录会被整体重建。真正稳定的做法是让 manifest 与 lockfile 的版本一致，或走插件自己的设置页。
- **安装/卸载本插件会重装整个 profile 的依赖**。`install_bundle` 底层是 pnpm 全量对齐，因此会「修正」任何被第三方插件在 `node_modules` 内私改的版本。给这类操作留出时间窗，不要在其前后立即重启。

## 3.6 度量

- **遵守率**：准备一组「先要求、后推翻」的对照对话，比较无插件 / 有插件时最终行为是否符合最新要求。
- **开销**：常驻区 token 占用、每轮增量请求字节、前缀缓存命中率变化。实测一段 215 条消息的会话台账稳定在 180 上下文 token 量级。
- **误报**：被判为要求的语句中，用户点了「撤销」的比例。首轮实现为 42 条 / 215 条消息，三轮校准后为 17 条 / 215 条，剩余条目人工复核均为真实要求。
- **稳定性**：同样的日志在多次恢复后的台账哈希是否一致（`renderLedger` 幂等性单测已覆盖）。

前三项决定这个插件是否值得长期开启，第四项决定它是否安全。
